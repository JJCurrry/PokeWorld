# ADR-006：交付评审的独立性、合规收口与「不改表」边界

> 意图层记忆：为什么这样设计。一页纸：背景 / 决定 / 被否决的备选及原因 / 后果。
> 状态：**G6 设计定稿（2026-11-16），实施中**；逐条机器证据以 `docs/工单/G6-内容扩充与交付评审.md` 为准。**AI 未自判通过、未写 G7 代码。**

## 背景（Context）

`docs/任务架构细分.md` §1 给 G6 的 DoD 是三条：「冷眼评审报告归档；六维合规自评更新；材料清单齐备」，目标含「8 潮灵 → 扩充、平衡调优、冷眼评审、软著材料清单」，委托级别「低委托 / **B + C 级**」。

2026-11-16 人分两轮答复「G5通过」「开始G6的开发吧」：前者关闭 G5 验收（人的裁决），后者授权开工 G6。延续 G3 / G4 / G5 的制度性边界：**本次授权不含改受保护三表 / 重建 `MANIFEST.sha256` / 重拍 `tests/golden_seed.json` 的逐次确认**。

于是 G6 面对一个结构性张力：

- 目标里的「8 潮灵扩充 / 平衡调优」**必须改表**（`species.json` / `encounters.json`）+ 重跑采样 + 可能触发 R7 快照 → 与「不含改表逐次确认」的授权边界直接冲突。
- DoD 三条（冷眼 / 六维自评 / 材料清单）**全部是文档与评审产出，不碰表** → 与授权边界相容。
- 人此前明确裁定「独立冷眼维持 G6」：G1–G5 只有实现者自审，不得冒充「已通过评审」。G0 的冷眼由**无开发历史、无本对话上下文的独立会话**产出（`docs/评审/G0-冷眼.md`），且「结论不得由实现者改写」。
- A4 目标档位仍是**原型级**，不做 SSSSSS 商业交付；`docs/GDD-v0.md` §8 六维自评是 G0 时点旧分（完整度 2/6、性能 2/6 等），到 G5 已明显过时，须按现状重评但仍守「不以 SSSSSS 名义交付」。
- 合规侧：人已裁定「自己玩无所谓」→ 自用不上架、不做商标检索与近似风险评估；软著材料清单须登记但「份数与格式以受理机构最新规定为准，AI 不作法律意见」。

## 决定（Decision）

1. **G6 本次只做三条不碰表 DoD；「内容扩充 / 平衡调优」拆出、等逐次确认**。冷眼评审、六维自评、软著材料清单全部是文档 / 评审产出，不修改任何 `data/*.json`、`MANIFEST.sha256`、`tests/golden_seed.json`；不改 G2 采样输入，按 G3 先例 S3-04 无需重跑 `balance_check.py`。潮灵扩充与平衡调优**不是本次 DoD**，须人逐次确认改表后才另开工单，不借 G6 顺手改表。

2. **冷眼由独立会话产出，实现者不改结论**。评审报告 `docs/评审/G6-冷眼.md` 须由无开发历史、无本对话上下文的独立评审会话只读产出，报告首行声明独立性；实现者只按其发现登记处置意见（接受并另开工单 / 说明理由），**不删改结论本身**。这是 G0 冷眼先例的延续，也是 A9「不把实现者自审冒充独立冷眼」的落地。

3. **六维自评按现状重评，仍守原型级定位**。`docs/GDD-v0.md` §8 按 G5 闭环后的真实状态更新每一维的分数、差距与补齐计划；明确最低分决定档位的规则不变，更新后仍不以 SSSSSS 名义交付；S3/S4/S5 已知缺口照登，不因打分上调而抹去。

4. **软著材料清单只做「清单 + 对应制品路径 + 待补动作」**。`docs/软著材料清单.md` 逐项列出源程序（前后各 30 页）、用户手册、设计文档、登记表信息项，标注仓库内对应路径与是否齐备；明确以受理机构最新规定为准、AI 不作法律意见，且不含任何规避监管的方法。

5. **零改表 / 零重建清单 / 零重拍快照**。全程由 `verify_all.py`（233 用例）、`gate.py`（R7 哈希锁 `3ab574e4…`）、`sha256sum -c MANIFEST.sha256`、`git diff 20787ea HEAD -- data/ tests/golden_seed.json = 0 行` 共同证明；逐笔提交 ≤5 文件 / ≤400 变更行；推送后 `git ls-remote origin HEAD` 核对。

## 被否决的备选及原因（Alternatives considered）

- **G6 顺手把 8 潮灵扩充 + 平衡调优做掉** —— 否决：要改受保护三表与重拍快照，本次授权明确不含改表逐次确认；无确认改表会撞不变量 #2 并破坏 R7 快照锁，须人逐次确认后另开工单。
- **由实现者自己写 G6 冷眼报告** —— 否决：违反 A9「不把实现者自审冒充独立冷眼」与 G0 先例；冷眼必须独立会话产出，实现者不得删改结论。
- **把六维自评「刷高」到 SSSSSS** —— 否决：A4 目标仍是原型级，性能 / 商业化 / 合规维度无实测支撑；虚高评分违反「不以 SSSSSS 名义交付」的既定规则。
- **把软著材料清单写成「已备齐、可直接提交」** —— 否决：源程序页序、用户手册成品、登记表信息均需人整理与核实，份数格式以受理机构为准；AI 不作法律判断，只登记清单与待补动作。
- **为「交付评审」重跑 `balance_check.py` / 重拍 golden 快照** —— 否决：G6 不改生成器 / 三表 / 公式，采样输入集合未变，快照变更须人逐次确认、本次授权未含。

## 后果（Consequences）

- 正面：G6 在不碰红线的前提下完成交付评审与合规收口，首次落实「独立会话冷眼」（G1–G5 缺失的质量机制）；六维自评与软著清单对齐 G5 闭环后的真实状态；全程零改表 / 零重建清单 / 零重拍快照。
- 负面 / 已知限制：冷眼发现的问题若需改代码 / 改表，须另开工单并由人裁决，本单不擅自返工；「8 潮灵扩充 / 平衡调优」继续挂起等人逐次确认，G6 名义里的「内容扩充」本次未交付；软著清单是待办清单而非成品材料，实际提交须人完成。
- 边界：G3 S3-01/S3-02、G4 S4-01~S4-05、G5 S5-01~S5-07 继续如实登记；冷眼结论只对当前链式拓扑与现有制品成立，不外推。
- **G6 交付时按 A9 将产生新的里程碑裁决项**（G6 是否验收 / 是否开工 G7 / 冷眼发现处置）；连同 B 组 2 项未答，届时以 `docs/接力文件.md`「待人类裁决的问题」+ 当前工单 + `docs/待裁定项.md`「说明」三处为准。AI 不自判通过、不预支结论。
